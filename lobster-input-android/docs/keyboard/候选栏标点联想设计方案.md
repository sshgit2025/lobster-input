- **该交互真实存在且是主流方向**（iOS 27 官方能力、百度与词语联想同流）。
- **标点候选挂在"联想"层，不挂布局层**——各家设置均不区分 9宫格/26键 ⇒ 三端 9宫格与 26键应同等待遇。
- **语义选标点规则全行业无公开文档**，唯一线索是讯飞语音侧"吗/什么/怎么→？"，需自行定义（本方案 §3）。

### 1.2 英文键盘（Gboard / iOS QuickType / SwiftKey）

**三家均不做"上屏后建议条按句意推标点"**。业界通行替代方案：
- 双击空格出句点（Gboard/iOS 均默认开）
- 标点后自动空格、标点贴词去空格、句末标点后自动大写
- SwiftKey 句号键右滑出 "?"

### 1.3 其他语种（日文/韩文）

- 日文 ATOK 是"输入句读点时触发转换确认"，非上屏后推荐；手机端未见该待遇。
- 韩文（Samsung/Naver）未见公开资料。

**产品决策：英文/俄文/韩文不做标点候选**（与业界对齐，避免画蛇添足）；本特性仅中文。

### 1.5 中文聊天标点使用习惯（用户研究，v2 补充）

- 莱顿大学 Lauren Fonteyn / 剑桥 Owen McArdle / David Crystal《Making a Point》/ 宾汉姆顿大学 126 人实验：短信/聊天中**句末句号被解读为不真诚、不友好、生气**；不加句号成为新默认（中国日报双语新闻 2020-09 报道）。

## 2. 总体设计

### 2.1 触发场景（与现有句子联想同门禁）

候选栏在「上屏词/句之后」进入联想态（composing 空 + `lastWord` 非空 + 中文模式 + 非密码框 + 非1键符号候选态）时，在联想候选流中注入标点候选。

**复用现有门禁，零新增分支维度**：

```
refreshCandidates() 联想分支:
  现状: emojis + engine.associations(lastWord)
  新:   punctCandidates + emojis + engine.associations(lastWord)
```

### 2.2 标点候选的位置：联想流头部

- 语义标点（"你好吗"→"？"）是此刻概率最高的下一动作，业界（搜狗/iOS）均给头部/常驻曝光位。
- 联想词顺序**完全不变**（用户 bigram 优先 > 内置兜底），标点只是在最前面插入 1~2 个槽位。
- `engine.associations()` 引擎函数**零改动**——注入发生在控制器层，引擎级历史电池天然不受影响。

### 2.3 点选标点候选的行为

| 行为 | 决策 | 理由 |
|---|---|---|
| 上屏方式 | 直接上屏该标点（**不走** SmartPunctuation 配对） | 。？！，非成对符号 |
| 用户词典 | 不学习、不调频 | 对齐1键符号候选 |
| lastWord | **不清空**（联想链不断） | 对齐历史修复"标点/空格不清空 lastWord" |
| 后续联想 | 点选后同一 lastWord **不再重复推荐标点**（词语联想继续） | 防"连点循环刷屏"；业界点完标点即回到词语联想 |
| 连续点选 | 允许（上屏多个标点），但点过一次后标点槽消失 | 同1键符号"可连点"哲学 |

### 2.4 抑制条件（任一命中则不注入标点，词语联想不受影响）

1. 密码框（沿用联想现有门禁，隐私）
2. composing 非空（打字态）/ `symCandidateMode`（1键符号态）——结构性不进入联想分支
3. 非中文模式（英/俄/韩不做，见 §1.2 调研决策）
4. **光标前文本以句读标点结尾**（，。！？、～…：；,.!?;:）——用户刚手动打过标点（含语音上屏的标点、外部编辑产生的标点），等下一个词再说。**闭合括号（）》"』」】] 不在抑制集**：`（测试）` 后推荐 `，`/`。** 是合理续写。
   - 实现方式（v2）：新增宿主能力 `textBeforeCursor(maxChars)`（安卓 `InputConnection.getTextBeforeCursor` / iOS `documentContextBeforeInput` / 鸿蒙 `getTextBeforeCursor`，三端均已有使用先例），**替代 v1 的 `lastCommitWasPunct` 手动标志位**——实时读文本覆盖语音上屏/退格/外部编辑等边界，且删掉一个控制器状态。
5. 同一 lastWord 已点选过标点（`punctConsumedFor == lastWord`）——**仅在取不到光标前文本时**（iOS 少数 App `documentContextBeforeInput` 返回 nil）的兜底抑制；取得到上文时以文本实时判定为唯一事实源（退格删掉标点后推荐自然恢复）
6. **单字中性上屏**（lastWord 长度=1 且未命中疑问/感叹词表）——多为逐字组词中途（9宫格逐字点选），出标点属噪音，抑制

### 2.5 Candidate 新标志 `isPunct`（关键隔离设计）

**绝不复用 `isSymbol`**，原因：
- `isSymbol` 触发候选栏**两侧收起契约**（2026-07-12 修复：符号候选13项需整行）。联想态本不收起（emoji 联想态不收起），若标点候选当 isSymbol 且位于首位 → 联想态两侧被收起 = 破坏历史契约。
- `isSymbol` 触发 SmartPunctuation 配对插入逻辑，`？` 不该配对。

新增 `isPunct: Boolean = false`：
- 不参与收起条件（收起条件仍只看 `composing非空 || 首候选isSymbol`）
- 点击走 `selectCandidate` 新增 `c.isPunct` 分支：直接 commit + 记 `punctConsumedFor` + 保 lastWord + 不学习
- UI 渲染与普通联想词候选完全一致（单字候选，现有 CandidateBarView 无需改版）

## 3. 语义标点规则（v2 上下文感知模型）

### 3.1 设计哲学（证据驱动，§1.4/§1.5）

1. **逗号是默认主力**：聊天场景逗号权重 > 句号（句号有"冷漠/生气"语义风险），句号**永不占首位**，只在中性长句/已有逗号时给第二槽。
2. **？/！ 按句型置顶**：疑问/感叹信号是高置信的"该收尾了"动作，给头部第一槽；第二槽给逗号（疑问/感叹后继续分句也常见："你好吗，我很好"）。
3. **规则小而硬编码**（语燕输入法验证的形态）：两张语气词表 + 一张连词表 + 两个上下文统计量，可解释、可调参，不引入模型。
4. **候选建议不自动上屏**：推荐候选由用户选择后上屏；未选择的建议不应改变已上屏文本；但"不合时宜的推荐"本身也是噪音，故设 §2.4 的抑制条件。

### 3.2 输入信号

| 信号 | 来源 | 说明 |
|---|---|---|
| `lastWord` | 控制器已有 | 最近上屏的词（词法规则作用对象） |
| `beforeText` | 宿主 `textBeforeCursor(64)` | 光标前 ≤64 字符（上下文规则作用对象；含语音上屏文本） |
| `clause` | 派生 | beforeText 截尾空白后，自最近句末符（。？！!?…～或换行）之后的片段 |
| `commaCount` | 派生 | clause 内 `，`/`,` 个数 |
| `clauseLen` | 派生 | clause 字符数 |

### 3.3 规则表（按序首个命中生效；输出 1~2 个标点，注入联想流头部）

| 优先级 | 类别 | 规则 | 产出 |
|---|---|---|---|
| 0 | 抑制 | 见 §2.4（刚打标点/单字中性/密码框/非中文/打字态/符号态/已点过） | `[]` |
| 1 | 疑问 | lastWord 尾部：吗 嘛 呢；包含：什么 怎么 为什么 谁 哪里 哪个 哪儿 哪些 哪天 何时 多少 多久 几点 难道 岂不 是否 能否 可否 可不可以 有没有 行不行 好不好 是不是 对不对 | `[？, ，]` |
| 2 | 感叹 | 尾部：啊 呀 啦 哇 呐 噢 呗 哟 加油；包含：笑死 气死 救命 绝了 好家伙 哈哈 累死 馋死 爱死 吓死 羡慕死 谢谢 感谢 恭喜 祝贺 辛苦；`太…了`（含"太"且尾"了"） | `[！, ，]` |
| 3 | 连词 | lastWord 精确命中：但是 可是 不过 然而 然后 接着 而且 并且 所以 因此 因为 如果 要是 既然 虽然 尽管 即使 哪怕 除非 由于 或者 还有 另外 首先 其次 比如 特别是 尤其是 对了 话说 顺便 总之 反正 其实 | `[，]` |
| 4 | 中性-发展中 | `commaCount ≥ 1` 或 `clauseLen ≥ 12`（本句已停顿过或已够长，收尾是真实选项） | `[，, 。]` |
| 5 | 中性-新开句 | 其余（短句开场，继续说话压倒一切；句号不强推） | `[，]` |

### 3.4 规则说明与取舍

- **疑问/感叹第二槽是逗号不是句号**：疑问句后接分句（"你好吗，我很好"）远常见过"你好吗。"；句号冷语义（§1.5）。
- **感叹词表**合并了语燕输入法的语气词集（啊呀呐啦噢哇吧呗了 → 取其子集，"吧/了"歧义大不入表）+ 中文聊天高频情绪词（笑死/救命/绝了，**包含匹配**覆盖"笑死我了"式后缀）+ 致谢类（谢谢/辛苦包含匹配；**"加油"仅尾部匹配**防"加油站"误伤）。
- **"太…了"模式**覆盖"太好了/太棒了/太离谱了"高频感叹句式；"真…"不收（误伤面大）。
- **连词表只收句首连接词**，收词标准是该词后逗号停顿为书写常态；故意排除"还是/最后/难道"（歧义或已入疑问表）。
- **`几`/`哪` 单字不入疑问表**（"茶几/窗明几净/哪怕"误伤），用"几点/多久/哪里/哪个/哪儿/哪些/哪天"等具体形式覆盖。
- **中性长句阈值 12 字**：聊天分句常见长度 4~10 字；≥12 字或已有逗号说明在写复合句，收尾概率显著上升。

### 3.5 点选行为（同 v1，不变）

直接上屏（不配对）、不学习、不清 lastWord；点选后光标前文本以标点结尾 → §2.4-4 自然抑制，词语联想无缝继续（讯飞实测验证的"标点双向"体验）。

### 3.6 设置开关决策（v2 不做，记录在案）

HeliBoard（默认关）与语燕（默认开）都有独立开关；百度把句号联想绑死词语联想开关是真实用户槽点。
本方案 v2 **不加独立开关**：现状词语联想本身无开关，标点推荐作为联想子集跟随同一默认开启策略，避免三端设置页扩散；若后续有用户反馈再单独加（届时参考 HeliBoard 的自定义标点列表）。
